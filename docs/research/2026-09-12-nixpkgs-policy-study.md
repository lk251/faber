# Nixpkgs cold-start study: NixOS nginx service verification

Research date: 2026-09-12. Repository snapshot: [`NixOS/nixpkgs@2f788abe393b6639416941926d53e106915f269d`](https://github.com/NixOS/nixpkgs/commit/2f788abe393b6639416941926d53e106915f269d), committed 2026-09-12 03:31:20 UTC. This was upstream `master` when retrieved. File citations below are immutable at that revision; issue and PR discussions are dated, mutable primary sources. The adjacent [source manifest](2026-09-12-nixpkgs-policy-study.sources.json) records fetched file hashes, historical pins, failed discovery paths, and scope limits.

**Finding:** nginx provides credible evidence that accepted scenarios and execution environments matter beyond a green build. It provides weak evidence that Faber deserves a separate product. Nixpkgs already has extensive domain tests, derivation identity, source-bound CI, reviewer routing, an explicit AI policy, and maintainers who request regression tests. A useful Faber increment would preserve a maintainer-approved relationship between a change, an invariant, a test, and its required environment. A CI wrapper, an LLM-authored checklist, or rediscovering tests is insufficient differentiation.

## Scope and research method

The bounded subsystem is `nixos/modules/services/web-servers/nginx/`: generated configuration, service identity and hardening, runtime directories, reload behavior, and the nginx side of certificate integration. Its verification surface includes the `nginx*` NixOS tests and the nginx variants of `nixos/tests/acme`. The generic nginx package expression is examined only to understand package/test links and build assumptions. DNS providers, the general ACME module, every downstream web application, nginx upstream C implementation, and all of nixpkgs are outside the claim.

This choice is deliberate: the module has recognizable owners, existing VM tests, difficult service-lifecycle behavior, and two useful historical cases. A 2023 incident failed after ten days of inactivity; a June 2026 change weakened the test environment and was reverted within hours. These are more informative than inventing an adversarial patch that an ordinary unit test would miss.

The work read current upstream raw files and GitHub API responses, then inspected the specific historic changes. No upstream code, Nix evaluation, build, VM, or container was executed. No maintainers were contacted. This is a source-grounded policy simulation, **not a measured defect-detection benchmark**. Local Windows access is not evidence that a Linux VM scenario passed. The inventory is bounded to the inspected assets; repository rulesets, all Hydra job outcomes, and all transitive application consumers were not exhaustively audited.

## 2. Proposed repository-owned policy, initially a draft

This is a proposal for a repository owner to accept or amend, not upstream policy and not an instruction to execute anything discovered in the repository. The bootstrapper may extract command descriptions and test IDs as data. Only a reviewed catalog may map those IDs to an executor. Candidate changes to policy, CI, test selection, or fixtures cannot weaken the requirements used to accept the same candidate.

| Task/risk class | Mandatory proposed evidence | Escalated / optional evidence | Human boundary |
|---|---|---|---|
| Documentation or option descriptions with no semantic change | Formatting/manual checks; diff classification supporting the no-behavior claim. | Evaluate relevant example configurations when defaults or executable examples change. | Reviewer resolves ambiguous “documentation-only” claims. |
| Generated HTTP configuration, locations or headers | Existing lint/eval checks, `nixosTests.nginx`, and named feature tests matched to changed option behavior; regression for the claimed change. | Relevant redirect, auth, proxy-protocol, HTTP/3, module or package-variant tests; two Linux architectures if architecture-dependent inputs change. | Owner decides expected protocol behavior and backward compatibility. |
| Systemd identity, hardening, paths, tmpfiles or listening sockets | `nginx`, `nginx-tmpdir`, `nginx-unix-socket`, and relevant home-directory/auth scenarios **in VMs**; inspect generated unit and runtime failure evidence. | New least-privilege, permission-denial and non-default identity scenarios where existing tests lack assertions. | Maintainer accepts capability/path changes and supported privilege configurations; no inferred security exception. |
| Reload, restart, configuration switching or ACME seam | `nginx`, `acme.nginx`, `acme.nginx-without-reload`; evidence for error reporting and retained active service after bad configuration. | Additional-vhost, renewal failure, cold boot and connection-continuity cases based on the changed behavior. | Maintainer approves downtime/error semantics and any certificate-handling change. Production DNS and real credentials are outside the default harness. |
| Package version, compiler flags, module ABI or supported platforms | Build affected package, its reviewed passthru tests/variants, and relevant module tests on applicable Linux architectures. | `nixpkgs-review` affected builds; representative downstream application integrations; platform-specific troubleshooting. | Release/backport/ABI scope and knowingly unsupported platforms need owner judgment. |
| Test infrastructure, VM-to-container migration, fixtures, check removal or policy changes | Compare old/new scenario and environment coverage; run impacted tests under the existing approved environment; record every removed assertion, disabled hardening feature and skip. | Explicit equivalence experiment in both environments, with a negative control that demonstrates the target invariant is exercised. | A human approves any changed coverage contract. Green results in a cheaper environment alone cannot approve equivalence. |

Environment requirements are explicit: a pinned nixpkgs revision, pinned CI tool inputs, sandbox enabled, Linux builder of the approved architecture, usable virtualization, disposable test state, and no production secrets. A container is a separate environment class. Upstream documentation specifically distinguishes VM support for service namespacing/hardening and specialisations from nspawn capabilities. [Environment distinctions](https://github.com/NixOS/nixpkgs/blob/2f788abe393b6639416941926d53e106915f269d/nixos/doc/manual/development/writing-nixos-tests.section.md#L134).

Each evidence record should contain base/head/test-merge revision, approved policy revision, harness/test-source revision, derivation identity, platform, VM/container class and relevant features, exact executed catalog ID and parameters, exit status, test assertions/log artifacts, execution time, and whether it was rebuilt or substituted. A cache result is useful but should be labeled; require an independent rerun only for the selected risk class. Preserve failure evidence, exclusions and human decisions as well as successes. These are proposed acceptance requirements; this research did not collect execution records.

For missing virtualization, unavailable platforms, ambiguous changed-path mapping, stale evidence, unclear owner, or a newly unsupported option combination, the status is `NOT_RUN` or `NEEDS_OWNER_DECISION`, never an inferred pass. A known failing mandatory test blocks machine acceptance. An optional check omitted by an approved policy stays explicitly optional. Changing the head or relevant harness invalidates the corresponding prior evidence. Urgent fixes can have a documented human exception tied to a precise revision and expiry; the model cannot grant one.

Reviewed command recipes for an eventual **trusted Linux checkout** include:

```sh
# Shared checks as defined by the inspected CI entrypoint.
nix-build ci -A fmt.check -A parse --keep-going

# Domain checks; source pins, sandbox settings and builder must be recorded.
nix-build -A nixosTests.nginx -A nixosTests.nginx-tmpdir \
  -A nixosTests.nginx-unix-socket --argstr system x86_64-linux
nix-build -A nixosTests.acme.nginx \
  -A nixosTests.acme.nginx-without-reload --argstr system x86_64-linux
```

These recipes were source-checked against registered attributes, not executed. Actual integration should reuse trusted CI orchestration and owner-approved runners, rather than execute a command string supplied by a cold-start extractor.

## 3. What cold inference can and cannot do

| Source / inference | Mechanical extraction | Reasoning layer | Owner or bespoke work |
|---|---|---|---|
| Structure, workflow and test configuration | Enumerate workflows, jobs, triggers, test files, attribute registrations, output artifacts, configured platforms and explicit dependencies. | Distinguish CI self-tests from service tests; identify that a file path is test selection rather than actual execution. | Confirm which status is required in live repository settings and whether external CI ran each scenario. |
| Build files and dependency graph | Extract literal `passthru.tests`, source hashes and module references; identify the missing tmpdir link. | Match a package/module/service change to relevant integration scenarios. | Full Nix evaluation is executable work requiring a sandbox and trusted evaluator. Static text alone cannot solve arbitrary Nix dependency evaluation. |
| Contribution docs and ownership | Extract stated review/disclosure rules, owners and test instructions with source references. | Reconcile custom ownership with empty test metadata and stale comments. | Determine who can approve a policy, expected service compatibility and availability for review. |
| Prior failures and PRs | Retrieve incident, patch, test addition, revert and commit relationships. | Propose “post-cleanup uploads remain functional” or “hardening evidence requires VM fidelity.” | Review scenario validity, applicability to current code and false-positive cost. |
| Missing assertions | Detect removed checks and changed test environment labels. | Explain likely loss of security/compatibility coverage and draft new scenarios. | Implement/test novel temporal, connection-continuity or permission harnesses; decide acceptable risk. |

Mechanically inferable material is enough for a **useful draft inventory and a conservative existing-test map**. It is not enough for a credible owner-approved policy. LLM reasoning can expose implicit dependencies and propose cases; it cannot invent who authorized them, what configurations customers rely on, which production downtime is acceptable, or whether a test actually exercises an attack condition. Historical comments are evidence of a problem, not authority to execute commands or change acceptance rules. No automatic percentage of policy completeness is defensible without an independently reviewed ground truth.

## 4. Historical policy evolution: actual failure and actual loss of fidelity

### Case A: nginx uploads fail after idle temporary-directory cleanup, 2023

The actual report [#257812](https://github.com/NixOS/nixpkgs/issues/257812) describes a running nginx proxy whose larger requests fail because a required `/tmp/nginx_client_body` directory disappears after inactivity. The report attributes this to tmpfiles cleanup and tentatively connects it to an earlier change; that introduction attribution was not independently bisected here. This is a service-lifecycle failure, not a compiler failure.

The remediation [PR #257828](https://github.com/NixOS/nixpkgs/pull/257828), merged 2023-10-06, adds tmpfiles exclusions and a regression test. Review explicitly requests a test that fails before the change and passes afterward. The test accelerates cleanup instead of waiting ten days, checks uploads before and after cleanup, and deliberately removes the directory as a negative control. [Historical test commit](https://github.com/NixOS/nixpkgs/commit/040cf48d2855175006d20ba90efbea5e438b3543), [repair commit](https://github.com/NixOS/nixpkgs/commit/ea1eb4ee0fa44dd4cd37e8ece2634370d1c2b0d2).

| Simulation element | Concrete result |
|---|---|
| Before policy | Plausible cold proposal from the pre-fix tree: evaluate/build nginx, boot the service, run existing nginx tests, inspect permissions. Unless explicitly designed otherwise, a short test need not trigger age-based cleanup. This is a reconstructed proposal, not a claim about an enforced historical gate. |
| Pinned pre-fix point | `3dfaa2a965f3ab82ab1f19c543c2917621c0014c`, parent of the added test commit. `040cf48d2855175006d20ba90efbea5e438b3543` introduces the regression before the repair; `ea1eb4ee0fa44dd4cd37e8ece2634370d1c2b0d2` repairs the module; merge is `c22f1c1cfa96e1bd87408aeebd0bab842b4e5157`. |
| Evidence available | User's runtime error, inactivity trigger and candidate workaround; maintainer discussion; executable test source; exact fix. These establish a real defect and regression design. This sprint did not rerun the historic failure/success pair. |
| Proposed learned update | Changes affecting tmpfiles, private temporary directories or nginx body buffering require `nginx-tmpdir` VM evidence. Include cleanup lifecycle behavior in the approved invariant map. Keep the intentional-removal negative control. |
| Automatic feasibility | High for proposing an existing test ID and mapping it to related paths after the incident. Moderate for drafting the accelerated reproducer from the report. Low confidence in finding this exact delayed interaction cold before any report; the desired negative control and safe resource/time bounds need review. |
| Strong baseline comparison | A competent agent given the same incident could write the same test; upstream humans already requested it. Faber's potential benefit is ensuring the regression remains selected on later related changes, not claiming exclusive discovery of the bug. |

Current `nginx-tmpdir` is a registry entry but not in generic nginx `passthru.tests`. An extractor can flag that mismatch for review; the strongest agent can flag it too. Whether it causes missed execution depends on actual CI selection and Hydra behavior. This study deliberately makes no missed-CI claim from that discrepancy alone.

### Case B: VM tests migrated to containers, then reverted for hardening coverage, 2026

[PR #536169](https://github.com/NixOS/nixpkgs/pull/536169) moved most nginx tests from `nodes` to `containers`; it merged at 2026-06-28 02:21:13 UTC. [PR #536256](https://github.com/NixOS/nixpkgs/pull/536256) reversed that change at 10:44:00 UTC, saying maintainer feedback required testing the hardening. This is a documented verification-design correction, not evidence of a production incident or proven false-pass in CI.

| Simulation element | Concrete result |
|---|---|
| Before policy | “Run the named nginx tests” leaves the meaning of their environment implicit. A test-only refactor could retain names and HTTP assertions while changing which system protections are exercised. |
| Pins | Original patch `b767296f886cf7a6fe23f913f58bfdd9d18e6e10`, parent `ae295d6c7bf1ce6348f61d868ac2c25d7814c0e0`, merge `4b8b28cce1a97752cf40973acb0b65b4243a0cd0`; revert patch `db155a44a08e5d738877e18d809058c7c8e2c280`, merge `fae7a03a83882ca5337e3e04f6d3ff0a3798e6b2`. |
| Observed evidence | Diff changes machine class across auth, tmpdir, home-directory, variants and other tests. Revert rationale identifies lost hardening coverage. Historical job logs were not independently checked; unchecked PR-template boxes are not proof tests did not run. |
| Proposed update | Tag hardening-related invariants with required VM features. Any change of machine class is an acceptance-policy change requiring owner approval and evidence of equivalence, even if existing assertions still pass. |
| Automatic feasibility | Mechanical detection of `nodes` → `containers` is easy. Reasoning from the service's hardening and driver limitations can propose a review block. Deciding that all affected tests must remain VMs is maintainer policy, as the actual revert illustrates. |
| Strong baseline comparison | A strong agent reviewing the test diff and driver documentation can raise this concern without Faber. Durable explicit environment requirements are useful only if they prevent recurrence more cheaply than a documented convention and CI guard. |

These cases motivate **coverage-policy drift**, including weakened environments and forgotten lifecycle regressions, as an experiment. They do not justify automatic claims that Faber would have prevented either incident. Testing that claim requires a time-separated, source-frozen experiment with outcome information withheld from the proposing agent.

### Temporal records and the policy-learning hypothesis

Policy authorship may be a learning problem: given a diff, repository context, previous accepted invariants and a cost budget, propose which evidence is needed, then learn from subsequent owner corrections and incident outcomes. The two cases support collecting that feedback. They do not establish that training improves over a frontier model with retrieval, or that a learned selector can become the acceptance authority.

The manifest contains two **retrospectively reconstructed** temporal rows. They preserve observed source facts and keep missing values null. Neither is a contemporaneous Faber trajectory or a training result.

The initial diff is therefore null in the machine row, rather than fabricated. |

Automatically observable strong features include an immutable changed-path/diff record, explicit machine-class replacement, pre-existing protection flags, registered test IDs, explicit reviewer test requests, and a later revert with a stated reason. Weak labels include “merged” as a proxy for correctness, “reverted” as a proxy for a proven bug, approval as a proxy for full policy acceptance, PR-template checkboxes as execution evidence, and elapsed time as labor cost. A revert can reflect a coverage preference; a long interval can mostly be queue delay. GitHub does not reveal the counterfactual outcome of a check that was never run, or the value of a defect that would otherwise have occurred.

Compare five approaches on the same frozen inputs: (1) explicit static change-to-test rules; (2) a frontier agent with repository context; (3) that agent plus retrieval of earlier incidents and accepted policy decisions; (4) a learned check router constrained to an approved catalog; and (5) learned structured policy proposals that still require owner approval. Report owner correction time and excess check cost as well as coverage. Chronological splits must exclude the June revert and post-incident rules from the June proposal inputs; keep related changes together so near-duplicate incidents cannot leak across the split. After a failure becomes known, evaluate policy evolution on **later different changes**, not by rewarding retrieval of the failure's own repair.

For this slice, simple routing plus retrieval is the leading hypothesis: the VM-fidelity concern was already written in the pre-change documentation. A trained policy author has to beat that strong baseline after label collection and maintenance costs. Sparse, selected and noisy public feedback is useful for constructing examples, but is not yet an economic data moat. A commercial loop would need consented owner corrections, actual check costs and outcomes from repeated use, with authority kept outside the model.

| Work | Estimate | Principal uncertainty |
|---|---|---|
| Generate an inventory and existing-test proposal | 1–3 engineer hours using a parser/agent; initial machine-only draft could be faster. | Custom ownership, dynamic Nix attributes and non-GitHub CI interpretation. |
| Establish a credible initial approved policy | Another 4–10 engineer hours plus 1–3 maintainer hours across one or two reviews. | Existing compatibility commitments, credible risk classes and environmental fidelity. |
| Configure a usable runner and evidence ingestion | 2–8 engineer hours if Nix/Linux builders already exist; 1–3 days otherwise. | Virtualization, cache trust, permissions, queue capacity and artifact retention. |
| Existing-verifier wiring | 1–4 hours for reviewed IDs and artifact mapping. | Preserving correct test selection without duplicating upstream orchestration. |
| Bespoke temporal or privilege regression | Roughly 4–16 hours per focused scenario; 1–3 days if substantial multi-machine/ACME debugging is needed. | Reproducing the actual fault, negative controls and avoiding flaky timing. |
| Routine policy maintenance | 0.5–2 maintainer hours/month for this slice, plus 1–4 hours per significant behavior/environment change. | Number and ambiguity of policy-change proposals. This is not a promise of low burden for all nixpkgs. |

Essential maintainer questions are: which non-default identity/home/socket configurations remain supported; which tests must exercise hardening in VMs; required architectures per risk; acceptable reload/downtime and certificate failure behavior; who approves exceptions; whether test substitutions are sufficient; and whether the tmpdir passthru discrepancy is intentional. The research continues without answers by marking these unresolved. A production policy cannot treat silence as approval.

A self-service adoption claim is therefore weak. The discovery work is relatively easy; the value and cost both lie in converting tacit intent into reviewed scenarios, maintaining that intent, and obtaining credible execution evidence. A vendor that owns none of those decisions risks becoming an extra dashboard and review burden.

## 6. Strongest baseline, product falsification and next experiment

The baseline should receive the same current repository, historical retrieval access, task budget and runner. It is a capable agent that reads contributing policy and workflow references, scans **all** nginx test registrations rather than just package passthru, inspects changed options and hardening, selects existing tests, writes a regression when needed, uses `nixpkgs-review` where appropriate, records ordinary CI artifacts and requests maintainer review. It can maintain a small checked-in change-to-test table and a CI rule guarding environment changes. This baseline is inexpensive and cannot be dismissed as “just run pytest.”

Faber wins only if it measurably improves **repeated acceptance decisions**: fewer missing required scenarios, less time asking maintainers what to run, fewer weakened test environments, better stale-evidence rejection, or lower cost per justified approval. Defect counts alone miss the fact that demanding every VM on every change can appear safe while making the workflow worse.

A minimal fair experiment is a held-out set of roughly 12–20 nginx module/test changes spanning configuration, lifecycle and environment changes. Use the two incidents above as development examples, never as hidden-test wins. Freeze the approved rules before evaluation; give baseline and Faber equal source visibility and compute limits. A maintainer, blinded to which output came from Faber, labels mandatory scenarios and irrelevant escalation. Measure selection recall, unnecessary mandatory checks, human correction time, check runtime, and unjustified acceptance. Separately replay the 2023 pre-fix/test-only and repaired revisions on disposable Linux VMs to verify the harness can reproduce the historical distinction. Do not back-project current policy into 2023 as if it existed then.

Proposed kill criteria, to be agreed before a pilot:

- If the agent plus a small CI mapping achieves the same accepted coverage with comparable maintainer correction time, kill the standalone policy-authoring product claim for this segment.
- If initial approval consumes more than one working day of maintainer time for this bounded slice, narrow the service or abandon self-service positioning.
- If additional requirements increase total review/compute burden without preventing owner-labeled missing evidence, stop expanding policy and test a simpler CI guard.
- If no team with an existing acceptance bottleneck will pay for a bounded policy-gap audit and regression delivery, technical interest from OSS maintainers is not commercial validation.

**Recommendation for this repository:** treat nixpkgs as an excellent adversarial benchmark and potential technical collaborator, not an evidenced first buyer. The most saleable output would be a fixed-scope, independently reviewed lifecycle/coverage audit for a company maintaining its own NixOS fleet or distribution. This study establishes the technical work such an offer would contain. It establishes neither a willing buyer nor a recurring software moat.
