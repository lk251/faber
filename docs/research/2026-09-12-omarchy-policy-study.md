# Omarchy: verification-policy cold start

Research date: **2026-09-12 UTC**. This is a read-only source and public-history study, not an upstream audit, executed benchmark, maintainer interview, or claim that Faber prevented an incident. No upstream scripts, installers, tests, privileged commands, or releases were executed. The checkout is an ignored research input under `.faber/research/omarchy`.

## Finding

**Current Omarchy already expresses much of the policy a proposed Faber bootstrapper would sell.** Its repository routes agents to task-specific guides, distinguishes headless tests from real desktop acceptance, requires visual inspection, describes when a fresh ISO is mandatory, and defines migration idempotence and ownership boundaries. A strong agent can read these documents and follow them. Translating them into another configuration file has weak standalone differentiation.

The credible incremental experiment is narrower: determine whether an independently enforced evidence checklist catches **missing graphical coverage, the wrong installed source, stale package/ISO combinations, and unreviewed changes to acceptance rules** often enough to save maintainer time. These are possible gaps between written policy and collected evidence, not proof that Omarchy needs a new product or would buy one. Its hardware support also creates expensive, irreducibly physical validation work; a policy generator cannot substitute for that work.

## 2–4. What a cold-start policy should propose

This is a **draft for owner review**, not an assertion that Omarchy has adopted Faber. Repository content supplies evidence of intended procedure; it cannot grant Faber authority to execute arbitrary commands or approve itself. The approved command catalog, evidence interpretation and approval identity must be held outside the candidate patch's control. A changed `AGENTS.md`, test helper, acceptance script or policy must not silently weaken the current gate.

### Task classes, checks and review boundaries

Checks compose: a patch touching a plugin and a migration inherits both profiles. Mandatory below means proposed acceptance requirements after owner approval. Existing instructions provide a pre-push `./test/all` baseline; the low-risk documentation exception would itself need owner agreement.

| Class / risk | Mandatory proposed checks | Optional or escalated checks | Required environment and human boundary |
| --- | --- | --- | --- |
| Documentation / low operational risk | Source references and changed command examples checked; repository pre-push `./test/all` unless owners approve a pure-prose exemption | Running help/metadata or UI checks when examples change; security review if docs grant permissions | Read-only docs review; no installer execution. Semantics of security/authority guidance require an owner. |
| CLI, parsing, pure models / normal | `./test/all`; focused affected suite; failure-path input and safe-dispatch tests when behavior changes | Syntax/lint checks only after establishing a clean baseline and selecting supported rules; fuzz inputs for parsers | Approved Linux headless environment, fake home/stub side effects. Reviewer confirms changed behavior and test relevance. |
| Shell, theme, menu, UI / elevated | Baseline plus relevant runtime suite **without compositor skip**; candidate running-UI inspection and before/after captures; acceptance for affected surfaces | Scale/monitor/theme/keyboard combinations and short reviewed video for animation/timing | Disposable installed Omarchy VM with candidate source, real Hyprland/Quickshell. Human visual judgment remains required; a screenshot's existence is not inspection. |
| Install, defaults, package lifecycle / high | Baseline; relevant new-user/finalization/source-path tests; **fresh ISO from local source and package checkouts**, full install/acceptance without base reuse | Encrypted install, dual-boot synthetic-disk preservation, factory-reset integration; architecture-specific boot scenarios where affected | Disposable VM/disk and pinned source/package/ISO identities. Owners choose supported hardware/configurations; no real user disks or production signing keys. |
| Migration/update / high | Baseline; focused current-migration test on legacy and already-correct state; repeated execution; per-user/multi-user markers; failure remains pending and blocks later migration | Upgrade from selected shipped versions, package skew/conflict and interrupted-update exercises | Fake-home tests first, disposable installed-system validation for privileged state. Maintainer decides supported upgrade populations and when a shipped migration test may be retired. |
| Privilege/authentication/security boundary / critical | Baseline plus named negative boundary regression; relevant installed-system security acceptance; explicit trusted-owner/security review | Adversarial input variants, persistent-state attack scenarios, privileged-file ownership and permission checks | Isolated approved VM with temporary test credentials only. New harnesses are reviewed before execution; agent inference cannot authorize new privilege grants or waive a failed boundary check. |
| Hardware/boot/audio / high to critical | Baseline; detector positive/negative fixtures; applicable fresh-ISO path; explicit hardware-evidence requirement for changed behavior | Real affected hardware, suspend/resume/reboot, mixed GPU/monitor and measured audio checks | State exact kernel, device IDs, driver versions and physical system; VM evidence covers only represented paths. Missing hardware becomes `HUMAN_REVIEW/UNVERIFIED`, never a compatibility PASS. |

The environment dispatch follows the actual upstream guide:

```text
Acceptance tests only:
  omarchy-iso-test <iso> --reuse-base --sync-omarchy <source> --no-preview
Runtime source with a compatible installed base:
  omarchy-iso-test <iso> --reuse-base --sync-all <source> --no-preview
Package manifests, installation, finalization or shipped defaults:
  omarchy-iso-make --no-boot-offer --local-source <source> <packages>
  omarchy-iso-test <fresh-iso> --no-preview
```

These are human-readable selections of documented sibling `bin/` entry points, not operational permissions or commands executed in this study. `--sync-omarchy` syncs the suite; it must not be misrepresented as testing all changed runtime source. `--sync-all` is a development convenience, not proof that packaging or a clean installation works. Global keybindings need the harness's QMP keyboard path; in-guest `wtype` is not equivalent. [Acceptance guide](https://github.com/omacom/omarchy/blob/31bd80daa4613ffdee995ac27467fce5a2990806/agents/skills/acceptance-tests.md).

### Evidence and uncertainty contract

Each accepted result should identify the reviewed base/head or candidate-tree digest, owner-approved policy revision, executor identity, exact invoked catalog capability, tool/runtime versions, environment image or ISO checksum, package-source pins, source-sync mode, and start/end time. Record expected, executed, failed, skipped and unattempted suites separately. Preserve exit codes, bounded raw logs, artifact hashes and the reviewer's attestation for visual/hardware evidence. Bind a privileged result to the disposable test environment and relevant installed versions, not merely a Git checkout.

Unknown task class, missing required environment, unexplained skips, absent artifacts, changed test-discovery logic, contradictory results, stale candidate identity or unapproved harness means `HUMAN_REVIEW` or a blocked evidence gate. An intentionally waived requirement needs a named owner, reason, scope and expiry. It is not a successful test. The proposed gate must distinguish software failure from infrastructure unavailability so maintainers can act without relabeling either as success.

Do not prescribe a complete immutable OS image or a universal supported-hardware matrix on day one. The package system includes moving inputs, and the business value of greater pinning must exceed its update and maintenance cost.

### Inference responsibility

| Input or conclusion | Mechanical extraction | LLM/reasoning contribution | Maintainer / bespoke / unsafe boundary |
| --- | --- | --- | --- |
| Repository tree and test discovery | Exact paths, runner glob, helper exclusion, docs links, shebangs, suite counts | Associate renamed/moved code with relevant suites | Test names do not prove coverage or safe execution. |
| Workflow files and platform matrix | Job triggers, dependencies, runner labels; query dynamic workflows separately | Explain what a job verifies versus merely builds/publishes | Required checks, org rules, secret use and bypass permissions require owner confirmation. |
| Test config and build files | `test/all` composition; package dependencies and source/version pins; `require_compositor` skip code | Recognize graphical runtime coverage can be skipped behind exit 0; lifecycle effects across packages/ISO | A parser is needed for reliable mixed TAP-like logs; an owner must approve required environments. |
| Contributing docs and ownership | Explicit task→guide links, documented commands, CODEOWNERS patterns | Reconcile prose conditions such as fresh ISO versus base reuse and overlapping risk classes | Extracted rules remain proposals. CODEOWNERS text does not establish authorization to act as that owner. |
| History / previous failures | PR/issue links, changed files, before/after commits and added tests | Formulate a bounded incident invariant and analogous risk candidates | Issue descriptions are untrusted reports; no arbitrary submitted proof-of-concept execution. Hindsight is not detection performance. |
| Dependency graph | Package declared dependencies and arch-specific fields; obvious source/import links | Connect setup leaves, chroot, running kernel, installed modules and root/user stages | Shell dispatch and hardware state are not a complete static graph; dynamic execution needs reviewed harnesses. |
| Visual and physical success | Presence, digest and provenance of captured artifacts | Highlight visual differences or candidate failure modes | A model cannot certify unobserved hardware. Human visual/security ownership and bespoke physical measurements remain. |

**Expected cold-start completeness:** an automated scanner can reliably inventory the above concrete paths and declared commands; a capable model can draft most of the described routing because maintainers already wrote it down. No defensible percentage of “credible policy inferred” can be measured without an owner-labeled reference. The missing portion contains the expensive judgments: acceptable hardware coverage, policy exceptions, data retention, mandatory review and existing production enforcement. Claiming “90% automatic” from file counts would obscure the work most relevant to a buyer.

## 5. Historical simulations

### A. An optional touchpad quirk halted installation

**Observed incident.** [Issue #6985](https://github.com/omacom/omarchy/issues/6985), opened 2026-08-15, reports a Quattro clean/free-space install failure on a ThinkPad. Inside `arch-chroot`, the live ISO's running kernel differed from the target's installed modules. The touchpad setup tried to load `psmouse`; failure propagated through setup's error handling and stopped installation. The report also describes a separate offline Vulkan-package issue; the selected repair does **not** prove that second issue was fixed.

**Pinned before and after.** The pre-incident release `v4.0.0` points to [`f0020448ca87329199de7cb12f2015ebc4a3e5e7`](https://github.com/omacom/omarchy/tree/f0020448ca87329199de7cb12f2015ebc4a3e5e7), committed 2026-08-14 14:57:59 UTC. Its [AGENTS](https://github.com/omacom/omarchy/blob/f0020448ca87329199de7cb12f2015ebc4a3e5e7/AGENTS.md) and [acceptance guide](https://github.com/omacom/omarchy/blob/f0020448ca87329199de7cb12f2015ebc4a3e5e7/agents/skills/acceptance-tests.md) already distinguish test-only sync, full-source sync and fresh-ISO requirements. The selected repair is [PR #7236](https://github.com/omacom/omarchy/pull/7236), merged 2026-08-24 as [`20400badda3862b5d533cadcb20730720360934d`](https://github.com/omacom/omarchy/commit/20400badda3862b5d533cadcb20730720360934d). Its immediate parent is [`535d8f3485581b35ab0d368d4179b362eb6dea32`](https://github.com/omacom/omarchy/tree/535d8f3485581b35ab0d368d4179b362eb6dea32). Before-source [`install/hardware/fix-synaptic-touchpad.sh`](https://github.com/omacom/omarchy/blob/535d8f3485581b35ab0d368d4179b362eb6dea32/install/hardware/fix-synaptic-touchpad.sh) loads the module after broad device-name and loaded-module checks; the patch adds a resolvability probe and treats later load failure as a warning. The added [`synaptic-touchpad-test.sh`](https://github.com/omacom/omarchy/blob/20400badda3862b5d533cadcb20730720360934d/test/shell.d/synaptic-touchpad-test.sh) stubs module commands and covers successful load, unresolved module, already-loaded state and load failure under an error-propagating source context.

| Stage | Policy simulation and limits |
| --- | --- |
| Policy before incident | The `v4.0.0` `AGENTS.md` already required focused tests and distinguished aggregate from disposable-VM acceptance; its acceptance guide already required a fresh ISO for installation changes. A faithful initial proposal would preserve that routing. It could not assume a generic VM exercised a Synaptics-named device path or the reported kernel/module mismatch. |
| Observed failure/evidence | Repeated install report with exact live/target kernel distinction; script control flow; PR root-cause explanation; before/after source and new regression tests. No execution was independently reproduced here. |
| Learned policy proposal | For **owner-designated optional hardware setup**, demonstrate that absent/unresolvable hardware and failed optional enhancement do not abort installation. Exercise sourced leaves with the caller's actual error semantics. Separate running-kernel operations from persistent target-system configuration. Require an explicit decision before adding persistent hardware overrides. |
| Concrete new evidence | Focused regression covers success, already-present, unresolved and failing module cases; install-path evidence represents live/target kernel mismatch; logs identify which hardware branch ran. Physical validation is still required if the change is meant to alter actual touchpad behavior. |
| Could it be automatic? | After the report and repair, an LLM can infer this narrowly and generate a draft fixture with high plausibility; the ordinary strong agent can do the same. Before the report, dependency reasoning might flag the chroot/running-kernel mismatch but no detection rate is known. The label “optional” and permission to continue after failure require owner judgment. Making **every** installation failure nonfatal would be unsafe. |
| Faber-specific value | Carry this invariant and its triggering paths into later review, require bound evidence, and notice omitted branch coverage. That is retention/enforcement value. The actual repair and regression already exist upstream, so replaying them cannot support a novel-bug-catching claim. |

The PR explicitly avoids persisting a module option because that would widen hardware behavior beyond the installation-stoppage repair. This is a useful example of a boundary that the policy should preserve rather than “complete” automatically. The release notes include the repair in [v4.0.1](https://github.com/omacom/omarchy/releases/tag/v4.0.1).

### B. A failing test hid later suites

[PR #6622](https://github.com/omacom/omarchy/pull/6622), merged 2026-08-08, changes `test/all` and `test/shell` from implicit error-stop loops into aggregate-failure runners. Parent [`007d6fcd7dd9bb992c3bd92ebd36db089f3b470f`](https://github.com/omacom/omarchy/tree/007d6fcd7dd9bb992c3bd92ebd36db089f3b470f); repair [`2b9e2720b33c3124b476d33362faef137d907605`](https://github.com/omacom/omarchy/commit/2b9e2720b33c3124b476d33362faef137d907605). The source comment records one packaging failure masking 114 of 134 files; the PR describes the growing suite as about 140 files. These are upstream historical observations, not current counts or independent measurements.

Before: running the aggregate produced nonzero at the first failure, so the old policy already blocked acceptance. The problem was missing diagnostics and repeated repair/rerun cycles, **not a false green**. After: continue independent suites, list failures, preserve nonzero overall, and retain first-failure exit inside each suite. The PR reports a scratch-suite validation for all-pass and first-file-fails paths.

A learned policy should require discovery/execution accounting and identify unattempted suites, with fail-fast explicitly labeled if chosen for cost. A small owner-approved synthetic runner fixture can verify first/middle/last failures without running product code. Generating this after reading the issue is ordinary agent work; interpreting it as proof that Faber uniquely prevented acceptance would exaggerate the evidence. Combined with today's compositor-skip semantics, it motivates the proposed evidence-completeness experiment, not a product conclusion.

## 6. Human burden estimates

These are planning ranges for a technically familiar maintainer plus an integration engineer, **not measured onboarding times or prices**. They assume a shadow-mode policy using existing suites and an available Linux VM host. New physical test devices, queued reviews and ISO runtime are separate calendar costs.

| Work | Initial human effort | Ongoing effort / uncertainty |
| --- | --- | --- |
| Validate inventory, choose scope, approve initial task classes | 2–4 hours engineer + 1–2 hours maintainer | 0.5–1.5 hours/week during active change; lower if the tool only reports |
| Connect existing test logs, distinguish skips, bind source/package/ISO identities | 4–12 hours engineer + 0.5–1.5 hours maintainer | 1–4 hours/month, potentially more when harness output changes |
| Establish repeatable VM workflow and visual artifact review | 4–12 hours engineer + 1–3 hours maintainer if a working host exists | Per relevant patch, roughly 10–30 minutes human review plus unmeasured machine time; installation failures can consume hours |
| One additional well-scoped mocked regression/harness | 2–8 hours engineer + 0.5–2 hours expert review | 0.5–2 hours per material interface/assumption change |
| New physical hardware or security-sensitive end-to-end verifier | 1–3 engineering days initially, sometimes substantially more, plus 2–8 hours domain review | Cannot be responsibly bounded across GPU, suspend, authentication and audio issues without access and agreed coverage |

A credible shadow pilot using existing environments is therefore approximately **10–28 engineering hours and 3–7 maintainer hours**, before new hardware/security harnesses. Adding every table row indiscriminately would overstate that pilot because some work overlaps. A fast document-only draft might take under an hour of machine effort and 1–2 human review hours, but it is not an integrated acceptance product.

Maintainer questions that automation cannot answer authoritatively:

1. Which written rules are enforced today, where, with which required checks/reviewers and bypass rights?
2. Which changes need a fresh ISO, which supported upgrade populations matter, and who approves exceptions?
3. Which physical platforms are release-blocking versus best-effort community support?
4. Is evidence stored in GitHub, an existing CI/artifact system, or elsewhere, and for how long?
5. Who owns policy edits, security exceptions, manual captures and temporary evidence waivers?
6. Is repeated evidence collection/review a meaningful time cost, or is patch quality/hardware access the dominant bottleneck?

Do not interpret missing answers as permission to make Omarchy's gates stricter or to delay its releases.

## 7. Fair baseline and falsification

The baseline is a **strong coding agent with the same source, history, model budget and tools**, not an agent that only finds a workflow filename. It reads `AGENTS.md` and linked guides, runs `./test/all` and focused tests, notices compositor skips, selects the documented ISO workflow, writes normal regressions, and attaches before/after visual artifacts. Add ordinary GitHub required checks and a competent reviewer. Permit the baseline to improve an existing CI wrapper or PR checklist; those are realistic alternatives to buying Faber.

| Capability | Strong agent + existing systems | Possible Faber increment | Candid conclusion |
| --- | --- | --- | --- |
| Discover commands and task guides | Already explicit; inexpensive to read | Cached, source-linked inventory | Weak differentiation |
| Propose regression after a detailed incident | Already demonstrated by upstream repairs | Durable proposed policy delta | No unique reasoning advantage shown |
| Detect headless graphical skips | Can read logs/helper and follow visual guide | Always classify required missing evidence independently of the candidate's report | Plausible small, testable increment |
| Bind the actual installed product | Can record source hashes, package versions and ISO checksum in CI | Reusable checks against a complete evidence subject across repositories | Plausible operational value if repeated mistakes exist |
| Validate actual hardware / UI | Requires suitable hardware and expert review | Route work and retain attestations | Does not eliminate the expensive work |
| Enforce owner policy across many agents | Existing GitHub checks, reviewers and CI wrappers can do it | Stable adapter and evidence contract across heterogeneous executors | Potential recurring value; superiority and budget unproven |

**Cheapest next experiment:** select six to ten public historical Omarchy changes spanning CLI, UI, migration and installation. Hide future fixes when doing before-incident evaluation. Have an independent reviewer label required evidence from contemporaneous documentation and reject hindsight requirements. Run the strong-agent/checklist baseline and Faber draft in shadow mode using the same read-only snapshots; use existing evidence where available and honestly mark missing VM/hardware execution. Then introduce clearly labeled synthetic evidence defects: compositor skip reported as complete, stale candidate SHA, test-only sync mistaken for source sync, reused ISO for changed defaults, and an edited acceptance helper that suppresses failures. These are artifact-handling tests, not real defect-detection rates.

Measure owner-accepted missing-evidence findings beyond baseline, false escalations, policy-edit burden, and reviewer minutes. Separately record whether the upstream code was actually executed and whether the difference is new testing versus simply correctly labeling evidence. Seek real recent-patch shadow use only after an owner agrees; do not contact anyone in this sprint.

**Kill criteria proposed for that experiment:** deprioritize a standalone Omarchy policy-authoring product if the strong baseline captures the same obligations; if owners reject most extra requirements; if setup needs more than two maintainer half-days before any saved work; or if added review/false-escalation time exceeds saved time. A simple CI wrapper and checklist winning is a valid result. A favorable result is several independently accepted, otherwise-missed evidence gaps with a materially lower review burden over repeated patches—not a polished bootstrap report or perfect performance on our own synthetic fixtures.

**Assessment:** technical evidence strongly supports that repository-owned policy exists and that acceptance spans more than headless CI. It does **not** yet support willingness to pay for Faber. Omarchy is a valuable falsification case and demonstration input; paying Linux vendors, fleet maintainers or teams supporting costly installations might be adjacent buyer archetypes, but no purchasing intent or budget was verified here. Do not treat Omarchy's project scale, agent usage or security fixes as sales qualification.

## Appendix: one chronological policy-learning example

This is a reconstructed **training-data candidate**, not a production Faber trajectory or proof that a learned model outperforms retrieval. Distinguish two prediction tasks: discovering an unknown failure before the first report, and choosing useful verification after a reported failure. Mixing them would leak the answer into the features.

Useful observable features are changed paths, call chain and sourcing/error mode, runtime-versus-target resource use, explicit environment names, existing test/catalog capabilities and cost, prior owner policy, issue arrival time, exact context documents exposed to the proposer, and bounded alternative check sets. The valuable labels are owner acceptance/rejection **with reasons**, execution result by environment, whether a concrete counterexample caused a repair, latency/cost, and later outcome. Public Git history gives some features and weak labels; it rarely gives the rejected alternatives, true proposal-time context, reviewer effort or reliable causal outcome.

A frontier model with retrieval over the same pre-report/pre-repair repository and a few similar historical incidents is the minimum fair policy-learning baseline. After the explicit report, the missing-kernel test is straightforward; fine-tuning may add little. Evaluate temporal holdouts and repository holdouts, owner-approved check utility per cost, unneeded escalations and never-taken alternatives. A history-derived dataset alone cannot estimate the counterfactual value of an unselected check. Start collecting proposal-time context and explicit feedback only during a consented pilot; do not build a universal training schema or infer customer data rights from public availability.
